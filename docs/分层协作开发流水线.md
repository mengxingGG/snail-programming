# 分层协作开发流水线

> 把这个文档发给 API 模型（Claude/GPT/DeepSeek/我），它会按流水线帮你拆分项目 → 在 `docs/` 下生成开发文档 → 你逐个取子文档丢给本地 Qwythos-9B 写代码 → 最后回来找 API 模型验收。
>
> **中大型项目节省 80-85% API 费用。**

---

## 目录结构约定

```
项目根目录/
├── docs/
│   ├── README.md          ← 主控文档（架构 + 模块清单 + 进度追踪）
│   └── modules/
│       ├── M01-认证服务.md
│       ├── M02-存储层.md
│       ├── M03-缓存管理.md
│       └── ...
├── src/                   ← 你的代码
└── ...
```

- `docs/` 下的所有文档都是本地 `.md` 文件，API 模型和本地模型直接读本地文件
- 飞书云文档只给人看（总结、方案讨论），不作为开发流程的一环

---

## 流水线四阶段

```
阶段 1：商议需求（你 + API 模型）
  → 讨论清楚项目要做什么、用什么技术栈、有哪些约束
  → 产出：项目需求摘要（聊完就有，不需要单独文件）

阶段 2：架构拆分（API 模型执行）
  → 传入：这个文档 + 需求摘要
  → API 模型在本地 docs/ 目录下创建：
      docs/README.md          主控文档
      docs/modules/M01-xxx.md 子文档×N
  → 产出：完整的 docs/ 目录

阶段 3：逐个开发（你 + 本地 Qwythos-9B）
  → 把 docs/modules/M01-xxx.md 的内容喂给本地模型
  → 本地模型按子文档写代码
  → 写完 → 本地跑测试 → 通 → 更新子文档末尾「开发状态」为 ✅
  → 重复下一个子文档

阶段 4：汇总验收（API 模型执行）
  → 传入：docs/README.md + 所有 docs/modules/*.md
  → API 模型做：逐模块审查 → 跨模块集成检查 → 最终验收
  → 产出：验收报告 + 修复清单
```

---

## 怎么用这个文档

### 使用方法

1. 先和 API 模型聊需求，把项目要做什么、技术栈、约束聊清楚
2. 把「本文档 + 需求描述」发给 API 模型，跑阶段 2
3. API 模型会告诉你 doc/ 下多了哪些文件
4. 逐个取 `docs/modules/M0X-xxx.md` 丢给本地 Qwythos-9B
5. 全部开发完成后，把所有文档发给 API 模型验收

## 子文档模板

每个子文档是本地 AI 程序员的**唯一输入**，必须自包含（不依赖其他文档）。

- **被依赖方**：哪些模块会调用本模块
- **预估代码量**：XXX 行

## 错误处理

| 错误场景 | 处理方式 |
|---------|---------|
| 输入 id 为空 | 抛 ValidationError("id 不能为空") |
| 依赖服务超时 | 重试 3 次（间隔 1s），仍失败抛 ServiceUnavailableError |
| 数据不存在 | 抛 NotFoundError |
| 格式解析失败 | 抛 ParseError，附带原始数据 |

### 验收文件
- `docs/README.md`
- `docs/modules/*.md`（共 N 个）

### 你的任务

**1. 逐模块审查**
对每个子文档：
- 接口完整性：是否实现了文档中定义的所有方法？
- 类型正确性：参数/返回值类型是否一致？

- 初始化顺序是否合理

## 关键原则

1. **子文档质量 = 代码质量上限** — 本地模型只看子文档，伪代码、错误处理、测试用例一个都不能省。
2. **子文档必须自包含** — 不要「参见 M03 接口」，把定义复制过来。
3. **开发状态是进度看板** — ⏳→🔨→✅ 就是你管理整个流水线的方式。
4. **先跑通一个模块** — 第一个模块全流程走通，确认模板没问题，再铺开。
5. **全中文即可** — Qwythos 基于 Qwen 基座，中文语料充足，不需要刻意用英文提示词。
